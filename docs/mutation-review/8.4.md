## Gaps closed (26 test cases added, 5 extended)

- **Account screen** (10 added, 3 extended):
  - A deposit named in the address is read only once the form options have loaded, and "Loading
    the deposit or withdrawal…" shows while it loads.
  - An edit address that arrives with a month change waits for that month's rows: the rows of the
    month on screen are kept while the next loads, and acting on them said the row was gone.
  - Focus: the first load leaves focus where it is; once the reload after a delete has arrived a
    later month change no longer moves focus to the Transactions heading; and browser Back from the
    Statements tab leaves focus alone, where the page's row focus recovery, if it also listened on
    that tab, sent it to an unrelated transaction row's button.
  - Deleting a row other than a credit refund leaves an open Pay card statement form as it is:
    reloading its statements empties the chosen card and disables Save until they arrive.
  - Counts toward tithe and Split to pots are ticked for a tithe category or a splitting source and
    can be unticked.
  - The transactions region is named by its heading, which takes focus without joining the tab
    order; the tab lists are named Card views and Pots views.
  - A failed first load shows only the error, with no header skeleton beside it.
- **Card statements** (11 added, 2 extended): months sort correctly across a year end and only the
  viewed year's month is marked; Status sorts paid statements by the day paid, an unknown day first;
  the viewed month scrolls into view (`block: 'nearest'`) once the statements arrive; while a payment
  saves every row action is disabled; the unmark dialog's buttons are disabled while it unmarks; a
  failed submit for want of a bank returns focus to Bank; the pay form submits without leaving the
  page; a bank load error shows with Try again, and none shows otherwise; opening the due date form
  on another statement moves focus to its field; the heading takes focus without joining the tab
  order; the bank picker's placeholder and the date field's changes are checked in existing tests.
- **Transactions grid** (5 added): a row with no round-up leaves its cell blank; settlement entries
  sort by note with blanks last; the Category filter offers no value for uncategorised rows (it
  offered "null"); a linked deposit's Edit is disabled while editing is unavailable but a card
  payment's statement link is not; the table takes focus without joining the tab order.

## Still undetected

All reviewed:

- **Equivalent** (15):
  - Fallbacks read only before the account has loaded, when nothing that uses them is on screen:
    the allowed actions (unknown names are dropped by `formActionsOf`), whether it is a card,
    whether it is active, and the currency of the pot and statements forms (5).
  - The row and operation delete dialogs' label and message fallbacks (4): the delete hook keeps
    its target after the dialog closes, so they are read only before the first request.
  - The post-save flag starting as set: its first run is at mount, before the heading or a selected
    tab exists for it to focus, and it clears itself there (1).
  - The page's row focus recovery also listening on the Pots tab (1): the pots table's rows hold no
    controls for it to record.
  - The settlement grid's Paid by and Note column keys emptied (2): the key is only used to pair a
    column with its sort accessor, which still pairs.
  - The grid's `default` branch emptied (1), which returns `undefined` either way; the pay form's
    focus effect given a constant dependency (1).
- **Accepted** (10): the action column's width class and the choice between its two widths (5), the
  viewed row's and numeric cells' class names (2), all styling; the statement row's React key (1),
  which only warns; and the unmark dialog's message and busy fallbacks (2), read once the statement
  is cleared, so they show only during Fluent's close animation, which jsdom does not run.

## Noticed

- The unmark dialog loses its message while it fades out: the statement is cleared as the dialog
  closes, so the message falls back to an empty string during the close animation. The delete
  dialogs keep their target and do not. Keeping the last statement until the dialog has closed is a
  small change for its own PR.
