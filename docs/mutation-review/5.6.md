## Defect found

The review of this slice found that closing the Suggest Values panel while its suggestions are
still loading does not stick: the late response sets the phase to `ready`, so the panel opens
again by itself (reproduced: closed, then `isOpen` true and phase `ready` once the load resolves).
The same race lets the first of two quick loads overwrite the second. `fetchSuggestions` has no
stale-response guard; `useLatestRequestGuard` already exists for this. The fix is left to its own
PR so this one stays test-only.

## Gaps closed (33 test cases)

- **Row focus recovery**: when the focused row goes away, focus moves to the same control in the
  next row (not just the last one), also when the table body is drawn again; a focused cell that
  is not a control is left to the page; an open dialog keeps focus while other parts of the page
  change.
- **Suggested values**: closed until opened; loads the month it is opened for; the load fallback
  message; the ticked count; an edited value is applied to its own row only; a negative edited
  value fails without being sent and nothing is reported as applied; the progress names the row
  being applied out of how many; the latest `onApplied` callback is called. The existing "continues
  past a failed row" test now has a row that was not applied and checks which rows failed, and the
  retry test counts the calls.
- **Recurring bill payment**: bills due the same day are ordered by description; the bills show
  as loading only while an open form waits for them, and not after a load error; choosing a bill
  clears the bill message; opening again or cancelling drops the bill, its field messages and
  the save message; editing a field and starting a payment clear the save message; a second
  submit while paying is ignored; a refusal is shown above the form when the bills cannot be
  reloaded after it. Existing tests now check that fixing one field leaves the other message, and
  that a second payment attempt clears the server's field message.
- **Card statement payment**: a card is named after its first statement; opening again or
  cancelling starts over with today and no field messages, and opening again drops the save
  message; the save message clears when a field changes and when a payment starts; choosing a card
  clears the card and statement messages, while changing the date clears only the date message;
  "nothing to pay" shows only once an open form has loaded an empty list; the form is dirty once a
  card with several statements, a statement or another date is chosen, and clean again once the
  card is unchosen. The existing "drops a statement that is gone" test now sends the form again
  and checks the save message is cleared.

## Still undetected

The last Stryker run (88.4%, 305 of 345) was before the last eight tests, which replaced looser
assertions (`toMatchObject` with `{}` matches any object, and a field change had already cleared
the message being checked) or were added by the review. A full run takes about two hours here, so
those were checked by hand: each mutation was applied to the source and the hook's test file run
against it. All eight are killed: the field messages kept on reset, the reset on cancel, the save
message kept on an invalid submit, the bill and messages kept on open and cancel (3), the
`onApplied` dependency, and the placeholder statement id of a card with several statements. That
puts the score at 90.7% (313 of 345). What is left, all reviewed:

- **Equivalent** (17):
  - **Card statement payment** (8): the "nothing to pay" conditions (7; the list is empty only
    once it has loaded, and it is null whenever the form is closed or loading for the first
    time); the date error key always set (an undefined message shows nothing).
  - **Recurring bill payment** (1): the check on an unparsed expense (it always parses when no
    field has an error).
  - **Suggested values** (6): the `OPEN` case removed (falling through to `CLOSE` and the fetch
    start gives the same state); four `useCallback` dependency arrays; the empty `catch` (the row
    status is already `error`).
  - **Row focus recovery** (2): finding a body that is still attached by index (it is the same
    body); the region ref in the effect dependencies (the ref object never changes).
- **Wording** (2): the payment fallback messages (1 each, bill and card payment).
- **Accepted** (13):
  - **Recurring bill payment** (2): the "loading" clause that covers the one render between
    opening and the load starting.
  - **Row focus recovery** (11): only visible across several renders or recoveries, or to code
    these tests do not reach:
    - the watcher not stopped after it recovers;
    - focus moving or a recovery not forgetting the row (3; only differs if the grid renders
      again later with focus lost);
    - the `focusin` listener of the watcher added or removed with a different flag or event name
      (3; the listener is left behind after one recovery and forgets the row on the next delete
      that opens a dialog);
    - the page listener not removed on unmount (2);
    - watching while focus is still inside the region;
    - the focus event guard, which only matters for focus coming through a portal.
