## Gaps closed (34 test cases)

- **Row focus recovery**: when the focused row goes away, focus moves to the same control in the
  next row (not just the last one), also when the table body is drawn again; a focused cell that
  is not a control is left to the page; an open dialog keeps focus while other parts of the page
  change.
- **Suggested values**: closed until opened; loads the month it is opened for; the load fallback
  message; the ticked count; an edited value is applied to its own row only; a negative edited
  value fails without being sent and nothing is reported as applied; the progress names the row
  being applied out of how many; the succeeded count and failed list leave out rows that were not
  applied; the latest `onApplied` callback is called; a retry of the failed rows sends them again
  (the existing test now counts the calls).
- **Recurring bill payment**: bills due the same day are ordered by description; the bills show
  as loading only while an open form waits for them, and not after a load error; choosing a bill
  clears the bill message; opening again or cancelling drops the bill, its field messages and
  the save message; editing a field and starting a payment clear the save message, and starting
  a payment clears the server's field messages; a second submit while paying is ignored; a refusal
  is shown above the form when the bills cannot be reloaded after it; the existing validation test
  now checks that fixing one field leaves the other message.
- **Card statement payment**: a card is named after its first statement; opening again or
  cancelling starts over with today and no field messages, and opening again drops the save
  message; the save message clears when a field changes, when a payment starts and when the form
  is sent again after its statement has gone; choosing a card clears the card and statement
  messages, while changing the date clears only the date message; "nothing to pay" shows only once
  an open form has loaded an empty list; the form is dirty once a card with several statements or
  a statement is chosen.

## Still undetected

The last Stryker run (88.4%, 305 of 345) was before the last seven tests, which replaced looser
assertions (`toMatchObject` with `{}` matches any object, and a field change had already cleared
the message being checked). A full run takes about two hours here, so those seven were checked by
hand: each mutation was applied to the source and the hook's test file run against it. All seven
are killed: the field messages kept on reset, the reset on cancel, the save message kept on an
invalid submit, the bill and messages kept on open and cancel, and the `onApplied` dependency.
That puts the score at 90.4% (312 of 345). What is left, all reviewed:

- **Equivalent** (21):
  - **Card statement payment** (9): the "nothing to pay" conditions (7; the list is empty only
    once it has loaded, and it is null whenever the form is closed or loading for the first
    time); the date error key always set (an undefined message shows nothing); the placeholder
    statement id for a card with several statements (an unknown id resolves to no statement).
  - **Recurring bill payment** (1): the check on an unparsed expense (it always parses when no
    field has an error).
  - **Suggested values** (6): the `OPEN` case removed (falling through to `CLOSE` and the fetch
    start gives the same state); four `useCallback` dependency arrays; the empty `catch` (the row
    status is already `error`).
  - **Row focus recovery** (5): finding a body that is still attached by index (it is the same
    body); the `focusin` capture flags (3; the event reaches the document either way); the
    region ref in the effect dependencies (the ref object never changes).
- **Wording** (2): the payment fallback messages.
- **Accepted** (10):
  - **Recurring bill payment** (2): the "loading" clause that covers the one render between
    opening and the load starting.
  - **Row focus recovery** (8): only visible across several renders, or to code these tests do
    not reach:
    - the watcher not stopped after it recovers;
    - focus moving or a recovery not forgetting the row (4; only differs if the grid renders

    - watching while focus is still inside the region;
    - the focus event guard, which only matters for focus coming through a portal.
