# Quickstart: Validating Application Observability

Validation scenarios for this feature once implemented, mirroring spec.md's User Stories 1–3. Not implementation steps — see `tasks.md` (generated by `/speckit-tasks`) for that.

## Prerequisites

- Repo built locally (`dotnet build`), `Financial.Web` built or running its dev server.
- Docker available for the optional observability containers.
- `data/data-cashflow.json` / `data/data-investment.json` present, or use the example files for a smoke run.

## Scenario A — Disabled by default (User Story 2 / SC-001)

1. Confirm `appsettings.json`'s `Observability:Enabled` is `false` (the shipped default) and no Jaeger/Langfuse container is running (`docker ps`).
2. Start the app the standard production way: `docker-compose up` (base file only — no overlay).
3. Exercise a few existing features (e.g. create an expense via `Financial.Web`, view an investment snapshot).
4. **Expected**: app starts and behaves exactly as before this feature existed; no errors in `logs/app-*.log` referencing telemetry export or a missing collector. `ITelemetryTracer` still resolves (it's backed by `NoOpTelemetryTracer`) — nothing in the app needs to know it's disabled.

## Scenario B — Enabled, backed by Jaeger (User Story 1)

1. Set `Observability:Enabled=true`, `Observability:Backend=Jaeger`, `Observability:Endpoint=http://localhost:4317`.
2. Start the Jaeger overlay: `docker compose -f docker-compose.yml -f docker-compose.observability.yml --profile jaeger up`.
3. Run `dotnet run --project Financial.Api` and perform one action from `Financial.Web`'s dev server (e.g. save an expense) — or from `Financial.App` (WPF) to validate FR-004a.
4. Open the Jaeger UI (default `http://localhost:16686`), find the corresponding trace.
5. **Expected**: one trace with spans for the controller/entry point, the explicit application-use-case span (e.g. `CashFlow.ExpenseService.CreateExpense`, set directly in the service method), and the storage write (`JsonStorage.Save`), correctly nested. No span attribute contains a raw amount, balance, or account identifier (spot-check against contracts/telemetry-semantic-conventions.md's allow-list).

## Scenario C — Switching to Langfuse with no code change (User Story 3)

1. Stop the Jaeger overlay; start the Langfuse profile instead: `docker compose -f docker-compose.yml -f docker-compose.observability.yml --profile langfuse up`.
2. Change only `Observability:Backend=Langfuse` and set `Observability:Langfuse:PublicKey`/`:SecretKey` to the local Langfuse project's keys; restart the app.
3. Repeat the same action as Scenario B.
4. **Expected**: the same connected trace now appears in the Langfuse UI instead, with no source-code changes between Scenario B and C.

## Scenario D — Backend unreachable (edge case / SC-006)

1. With `Observability:Enabled=true` and no observability container running at all, start the app.
2. Exercise existing features.
3. **Expected**: app starts and functions normally; telemetry export failures are silent to the user.

## Scenario E — Verify the isolation constraint itself (SC-008)

1. Run a project-reference audit: `dotnet list Financial.Api/Financial.Api.csproj reference` (and equivalently for every other project) or inspect each `.csproj`'s `PackageReference` entries.
2. **Expected**: `OpenTelemetry`-prefixed package references appear **only** in `Integrations/Observability/Integrations.Observability.csproj`. `Financial.Shared.Abstractions` has zero package or project references at all (enforced by `SharedAbstractionsDependencyRuleTests`). Every project that records telemetry (`Financial.CashFlow.Application`, `Financial.Investment.Application`, `Financial.Shared.Infrastructure`, `Financial.Api`, `Financial.App`) references `Financial.Shared.Abstractions` only, never `Integrations/Observability` or the OpenTelemetry SDK directly.
